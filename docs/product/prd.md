# PRD：梅西影像档案库

## 1. 问题陈述

梅西相关图片资料散落在社交平台、新闻网站、球迷账号和个人网盘中，存在时间不准、来源不清、分类混乱、重复图多、检索困难、高清版本难找等问题。用户想建立一个长期可维护的图库站，用于后续查阅、考古和中文球迷资料沉淀。

## 2. 产品定位

产品是“梅西影像档案库 + 轻社交 + 赞助支持”。

它不是官方站，不是后援会，不做版权内容售卖。赞助会员的含义是支持网站可持续维护，不是购买图片版权或解锁盗版图片。

## 当前生效规则（2026-09-09）

- 图片发布只要求选择 生涯阶段、年份、场景 3 个必选主分类；其他主分类可选，管理员可继续维护各主分类下的子分类。
- 不选择相册也可以独立上传和管理图片；相册仅是可选的组织方式。
- “上传批次 / 批量整理”现为只读“上传任务”记录；所有图片编辑和批量操作统一在图片管理完成。
- 智能标签已下线；OCR 仅按需使用，默认关闭且不阻塞上传发布。
- 上传窗口默认选择“处理完成后自动发布”；发布失败或条件不完整时保留草稿，图片管理列表提供单张发布入口。
- 图片管理列表提供单张发布、批量确认发布、批量改草稿和归档操作；已发布/已归档记录的发布按钮不可用，编辑表单中的发布状态和发布时间由系统状态维护，不作为普通元数据随意修改。
- 每张图片上传后都会异步生成展示图和缩略图：local 使用 PHP GD 生成 WebP，COS 使用腾讯云数据万象生成 WebP；展示图最大 2048×2048，缩略图最大 600×600，成功后统一写入 `display_key` 和 `thumbnail_key`。
- 展示图/缩略图生成失败会记录处理任务和失败原因；图片缺少任一派生图时不能发布。处理任务由常驻队列 Worker 消费，宝塔计划任务 `schedule:run` 不替代 Worker。
- 图片管理列表每行只显示一个真实缩略图，支持悬停预览展示图；不显示缩略图地址，也不重复渲染同一缩略图。

## 3. 用户角色

| 角色 | 核心目标 | 主要权限 |
|---|---|---|
| 游客 | 浏览公开图片、相册和专题 | 浏览、搜索基础公开内容、分享公开页面；无需登录即可浏览全部公开内容 |
| 普通用户 | 收藏、互动、参与轻社交 | 登录、收藏、点赞、评论、举报、分享、佩戴勋章 |
| 运营守护者 | 赞助网站维护 | 普通用户权限、守护者徽章、运营守护者页展示、可选无广告/更高配额 |
| 编辑员 | 维护图片资料 | 上传图片、编辑图片元数据、管理相册、处理待考证资料 |
| 管理员 | 管理全站 | 用户、权限、订单、评论审核、系统设置、数据处理任务 |

## 4. 功能优先级

### P0：第一版必须完成

1. 管理员/编辑员后台登录。
2. 图片上传到可配置图片存储，本地存储和腾讯云 COS 两种方式都可切换；生产环境优先使用 COS/CDN。
3. 图片档案基础字段：标题、日期、相册、分类子项（含球队、赛事、赛季、年份等）、标签、来源、版权状态、审核状态。
4. 后台上传任务记录：记录批量上传结果、失败原因和处理状态；图片编辑、批量分类、批量发布和归档统一在图片管理完成。

6. 前台图库浏览：首页、图库列表、搜索页、相册列表、相册详情、专题列表、专题详情、图片详情；首页包含“最新照片”模块。
7. 基础检索：关键词、相册、分类子项（含年份、球队、赛事等）、标签。
8. 图片缩略图与展示图。
9. 本地任务和开发规范文档。

## 5. 用户故事

1. 作为游客，我想按年份查看梅西图片，这样可以快速回到某个生涯阶段。
2. 作为游客，我想进入某场比赛的相册，这样可以按事件考古。
3. 作为普通用户，我想收藏图片，这样以后可以快速找回。
4. 作为普通用户，我想评论图片，这样可以参与讨论。
5. 作为普通用户，我想对图片补充信息或提交纠错，这样可以帮助编辑修正时间、来源、事件或人物信息。
6. 作为普通用户，我想举报不当评论，这样社区内容能被维护。
7. 作为运营守护者，我想通过赞助支持网站，这样站点能长期维护。
8. 作为运营守护者，我想显示守护者徽章，这样能表达我对项目的支持。
9. 作为普通用户，我想通过任务或纪念日获得并佩戴勋章，这样能留下参与网站的身份印记。
10. 作为编辑员，我想批量上传图片，这样能高效整理历史素材。
11. 作为编辑员，我想给图片选择分类子项（如赛事、球队、赛季、年份）和标签，这样前台用户能检索。
12. 作为编辑员，我想看到重复图和相似图提示，这样能减少图库污染。
13. 作为管理员，我想审核评论，这样能降低 UGC 风险。
14. 作为管理员，我想查看赞助订单和支付回调，这样能排查支付问题。
15. 作为管理员，我想查看图片点赞、评论、收藏和转发排行榜，这样能了解轻社交互动热度。
16. 作为管理员，我想管理勋章、获取任务和纪念日发放，这样能维护用户成长体系。
17. 作为管理员或编辑员，我想审核用户投稿，通过后再进入图片整理和发布流程，这样普通用户投稿不会直接公开。

## 6. 不做什么

第一版不做：

- 普通用户直接公开上传图片。
- 图片版权交易。
- 付费解锁原图。
- 完整论坛、私信、关注流。
- 自动识别梅西以外所有人物并自动发布。
- 微信小程序支付闭环。
- APP。
- 多语言。
- 商业图库授权。
- 通用 CMS 页面管理。

## 7. 验收标准

P0 完成时，应能做到：

- 管理员能上传并管理图片，批量上传后能进入上传批次进行批量整理。
- 首页能展示“最新照片”，包含最新发布的相册图片和单独上传图片。
- 前台用户能按相册、分类子项（含年份、球队、赛事等）和标签检索图片。
- 每张图片有来源和版权状态字段。
- 图片文件通过可配置存储管理；生产环境优先走 COS/CDN，本地存储仅作为开发或过渡方式。
- 后续 P1/P2 功能有清晰任务入口。


## 8. 档案共建者、权限与分类删除方案（2026-09-12）

### 8.1 档案共建者的业务定位

“档案共建者”是面向前台展示的贡献身份，不是新的高权限管理员角色，也不代表金钱赞助关系。项目不提供公开申请、公开审核或公开通过流程。共建者只通过私域沟通产生：管理员确认参与意愿，用户自行注册普通账号，管理员在后台用户管理中人工授予共建者身份和编辑员内容权限。

系统不保存共建申请、申请审核、申请通过等公开业务状态，也不在前台展示申请入口。

### 8.2 角色与权限边界

系统权限角色仍然只有 user、editor、admin 三类。档案共建者是展示身份，实际内容操作权限由 editor 角色提供。

| 身份 | 可执行操作 | 明确禁止 |
|---|---|---|
| 普通用户 | 浏览公开内容、收藏、点赞、评论、举报和个人资料维护 | 进入后台内容管理 |
| 编辑员 | 普通用户全部能力；维护图片、相册、分类、标签、来源；执行档案整理和发布 | 用户管理、角色管理、支付、赞助订单、系统设置、安全配置、管理员账号操作 |
| 管理员 | 管理全站用户、权限、内容、审核、赞助、支付和系统设置 | 仍需遵守数据删除保护和操作审计规则 |
| 档案共建者 | 对外展示贡献身份；实际使用编辑员内容权限 | 不因展示身份获得额外管理员权限 |

撤销共建者时，默认同时撤销共建者资料和编辑员权限并恢复普通用户身份。若未来存在多个独立编辑授权来源，再增加授权来源记录，不能直接误降权。

### 8.3 支持本站与前台入口

支持本站页面分为两类：运营守护者由支付成功或后台确认订单后进入致谢墙；档案共建者由管理员人工授予并确认公开展示后进入共建者名单。共建者展示资料包括昵称、头像、简介、贡献方向、公开状态和排序，不展示私域沟通记录、内部备注或未经确认的个人资料。

前台登录后的个人中心菜单始终提供个人中心和退出登录；只有管理员或编辑员显示管理后台。前台 /login 与后台 /admin/login 使用同一用户表、认证守卫和会话，不创建第二套用户体系。

### 8.4 分类删除规则与用户提示

8 个系统主分类和系统保留子分类不可删除。没有图片、相册或子分类引用的普通子分类允许删除；已有关联的普通子分类禁止删除，优先改为隐藏。

删除动作必须在后端检查图片、相册和子分类引用数量，并在事务内执行。存在引用时显示业务通知而不是返回 Livewire 500，提示至少包含关联数量，例如：“无法删除该分类：已关联 12 张图片、3 个相册。请先移除关联，或将分类设置为隐藏。”

photo_category 和 album_category 均不允许数据库级联删除；管理员必须先移除关联，才能删除没有引用的普通子分类。删除动作还必须捕获并转换并发情况下的外键异常。

### 8.5 开发切片与验收标准

第一切片为分类删除保护：增加引用检查和统一提示；保留系统分类保护；补充安全外键策略；增加未关联可删、已关联拦截、系统分类拦截测试。

第二切片为用户管理与档案共建者：增加共建者资料和后台授予、编辑、撤销操作；授予时赋予 editor 角色；限制编辑员资源；补齐前台两类支持名单、个人中心管理后台和退出登录；补充管理员、编辑员、普通用户权限测试。

验收必须覆盖：未关联子分类能删除；已关联分类只显示业务提示且不返回 500；系统分类继续受保护；管理员可人工授予和撤销共建者；编辑员不能进入用户、支付和系统设置；前台只公开已确认展示的共建者资料。
### 分类删除保护实现记录（2026-09-12）

分类管理已完成第一阶段的安全闭环：系统分类不可删除；已被子分类、图片或相册引用的分类不可删除并显示关联数量；无引用的普通分类可以删除；数据库外键和后台动作同时提供保护，避免误删关系或显示页面级错误。

### 管理员用户治理与用户头像（2026-09-12）

管理员在 `/admin/users` 中维护基础资料、手机号和头像；通过独立动作完成角色调整、启用、停用、封禁、解封和强制退出全部会话，并在编辑用户窗口直接重置登录密码。重置密码不发送邮件，保存新密码后使该用户已有会话失效；支持批量启用、停用、封禁和解封。角色仍只有 `user`、`editor`、`admin`，不新增动态用户组。活动档案共建者必须先撤销，再调整角色，以保护既有角色快照和撤销恢复逻辑；最后一名有效管理员不能被降级。

用户注册时必须填写唯一的中国大陆 11 位手机号；已有用户可以在 `/settings/profile` 补充或修改手机号。手机号用于账号资料和联系方式，不作为登录凭据，也不开发短信验证码。用户可以在 `/settings/profile` 上传、替换和移除头像，管理员也可以在用户编辑表单中代维护头像。头像只接受 JPG、PNG、WebP，最大 2MB；头像文件复用当前 local/COS 存储切换，公开资料、共建者名单和已登录用户只接收解析后的公开 URL，不暴露存储键。管理员操作写入审计，认证登录写入登录历史。

本项目不开发、也不纳入待办的企业级权限能力包括：动态用户组、多个角色并存、细粒度资源 ACL、可配置角色权限组合，以及通用权限优先级和冲突处理。固定的 `user`、`editor`、`admin` 三角色已经满足图片档案库的业务需要；普通用户直接上传图库图片同样不开放。
### 档案共建者阶段 2A 实现状态（2026-09-12）

阶段 2A 先完成用户管理与授权基础；前台共建者名单随后已在阶段 2B 完成。当前产品行为是：管理员在 /admin/users 中对已注册用户人工授予档案共建者资料；普通用户被授予时获得 editor 内容权限；撤销时只恢复本次授权产生的角色，不影响原有 editor 或 admin。阶段 2B 才实现 /supporters 的共建者公开展示、贡献方向和展示排序。生产环境测试已在档案共建者阶段完成后执行并通过。


### 档案共建者阶段 2B 实现状态（2026-09-12）

阶段 2B 已完成用户管理与前台展示闭环：管理员可以编辑共建者展示名称、简介、贡献方向、公开开关和展示顺序；/supporters 分开展示运营守护者与档案共建者；公开数据不包含内部授权字段。项目仍不提供公开申请和审核流程，生产环境迁移和验收已完成。
