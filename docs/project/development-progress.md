## 项目总目标

建设一个面向梅西影像资料整理、检索和长期考古的图库网站。

项目长期形态是：

- 一个可持续维护的梅西图片档案库。
- 一个支持多维分类、标签、时间、来源检索的图片资料站；赛事、球队、赛季、年份等通过分类子项表达。
- 一个未来可以逐步加入轻社交、赞助会员、腾讯云智能处理和微信小程序能力的内容平台。

项目第一原则：先保证资料能被稳定录入、整理、检索和展示，再逐步增加互动和商业化能力。

## 阶段路线图

### Phase 0：项目初始化与规则建立

目标：把项目地基搭好，让后续 AI 开发有明确规则和上下文。

范围：

- 初始化开发前文档。
- 确定技术栈。
- 建立 Git 仓库和提交习惯。
- 建立 AI agent 协作规则。
- 初始化 Laravel 项目骨架。
- 配置本地开发环境。
- 配置后台中文化。

状态：已完成。

### Phase 1：图库核心 MVP

目标：完成图库最小可用闭环。

范围：

- 图片数据模型。
- 相册/专题模型。
- 图片分类模型。
- 标签模型。
- 人物关系标签。
- 赛事、球队、赛季、年份等分类子项。
- 图片来源字段。
- 后台图片上传和管理。
- 后台批量上传到相册。
- 后台批量整理图片。
- 后台相册/专题管理。
- 后台分类子项、标签和来源等基础字典管理。
- 前台图片列表页。
- 前台图片详情页。
- 基础关键词搜索。
- 基础筛选：分类（含赛事、球队、赛季、年份等子项）、标签、时间。
- 少量测试数据录入。

第一版成功标准：

- 管理员可以从后台上传一张图片并填写基础资料。
- 图片可以在前台列表中展示。
- 图片可以进入详情页查看。
- 用户可以通过基础条件找到这张图片。
- 整个流程不依赖评论、会员、小程序或 AI 图片能力。

状态：已完成。P0 / Phase 1 图库核心 MVP 已完成并通过 P1-13 总体验收；后续只做补漏或增强，不再作为当前开发阶段。

### Phase 2：图库检索与资料增强

目标：让图库更适合长期考古和高效查找。

范围：

- 高级筛选组合。
- 图片清晰度、尺寸、横竖图、水印状态。
- 来源可信度扩展。
- 时间轴浏览。
- 赛事专题页；专题主要由多个相册组成，额外负责导读、关联相册组织、精选展示和时间线串联。
- 球队/赛季/对手维度。
- 批量编辑图片信息。
- 后台批量导入优化。
- 图片重复提示的基础人工流程。

当前已完成：

- 基础关键词搜索、相册、分类子项、标签和时间筛选已在 P0 / Phase 1 完成。
- 专题列表、专题详情、首页专题入口和相册组织基础已完成。
- 后台批量上传、上传批次和批量整理基础已完成。
- 后台图片管理精确 SHA-256 重复图提示已在 P1-11 完成。
- 高级组合筛选、清晰度、来源、版权状态、人物同框、横竖图和水印状态筛选已在 P1-15 完成。

仍未开发：

- 球队 / 赛季 / 对手等更深资料聚合页面。
- Meilisearch 或 Typesense 外部搜索引擎接入。
- 相似图推荐、相似图分组、以图搜图和自动去重。

状态：部分完成。基础检索、专题、批量整理、数据库内高级组合筛选、时间轴浏览、球队 / 生涯阶段聚合、赛季聚合、对手聚合、搜索建议 / 热门搜索 / 后台搜索运营配置已完成；外部搜索引擎和相似图能力仍未开始。

### Phase 3：腾讯云 COS 与数据万象接入

目标：让图片存储和智能处理逐步接入真实云服务。

范围：

- 腾讯云 COS 存储桶配置。
- 图片上传到 COS。
- 图片访问域名和防盗链策略。
- 数据万象基础图片处理。
- EXIF 读取。
- OCR 识别结果存储。
- 感知哈希字段预留和计算。
- 相似图去重工作流。
- 以图搜图可行性验证。

注意：Phase 1 不依赖本阶段。第一版可以先用本地存储或模拟字段完成业务闭环。

当前已完成：

- Laravel 文件系统抽象和本地 public 磁盘展示链路已跑通。
- 图片上传后系统重命名、保存原始文件名、文件大小、MIME、宽高、原图路径、展示图路径和缩略图路径等基础信息。
- P1-11 已落地 `photo_analysis_results`、`processing_jobs`、基础 metadata/hash 处理任务和后台处理队列页面。
- 后台图片管理已支持基于 SHA-256 的精确重复图提示。

仍未开发：

- 腾讯云 COS 真实存储桶、访问域名、防盗链、CDN 和生产切换。
- 腾讯云数据万象生产验证和正式部署仍未完成；当前 6 张 COS 业务原图已完成展示图/缩略图、智能标签和相似候选真实处理，OCR 对无文字图片已记录明确失败原因；图片质量评分不纳入项目范围。
- 感知哈希、相似图索引、相似图分组、相似图推荐和以图搜图。
- 生产队列 Worker、重试告警、批量失败恢复和运维监控。

状态：部分完成。本地存储、基础入库处理、精确哈希重复提示、COS 配置边界、数据万象派生图处理、相似图首个后台辅助切片、OCR / 智能标签处理和上传发布体验增强已完成；当前 6 张 COS 业务原图真实处理已验证，COS 生产切换、历史图片迁移、生产 Worker / 监控和相似图二期仍未完成，图片质量评分明确不纳入项目。

### Phase 4：轻社交功能

目标：在图库稳定后，增加低强度互动能力。

范围：

- 用户注册和登录体验优化。
- 评论。
- 点赞。
- 收藏。
- 分享。
- 举报。
- 内容审核。
- 互动统计与排行榜。
- 勋章、成就任务和纪念日发放。
- 用户个人页的基础形态。

注意：轻社交要控制边界，不能让项目从图库站变成重社区。

当前已完成：

- 普通用户注册、登录、退出、找回密码和前台身份入口已完成。
- 图片收藏、点赞、分享记录基础已完成。
- 图片普通评论、图片信息补充 / 纠错投稿、评论审核、举报、封禁和敏感词基础过滤已完成。
- 用户中心、通知中心、互动统计、前台排行榜、后台互动统计和基础勋章 / 成就已完成。

仍未开发：

- 微信 / 微博等第三方分享 API、分享海报生成和短链接。
- 复杂社交动态流。
- 后台互动管理、异常刷赞处理和排行榜管理。
- 公开用户个人主页、关注关系、私信、评论点赞、公开勋章大厅和运营活动配置。

状态：基础完成。P1 已完成轻社交基础闭环；复杂社交、第三方分享和运营治理增强仍未开始。

### Phase 5：会员与赞助

目标：支持网站可持续运营，不把 VIP 设计成图片版权售卖。

范围：

- 普通用户。
- VIP 用户。
- 赞助记录。
- 微信支付。
- 赞助权益展示。
- 后台会员管理。
- 支付回调和订单状态。

原则：

- VIP 是赞助支持，不是购买图片版权。
- 第一版不做付费内容墙。
- 涉及支付前必须先补充合规说明和退款/异常处理流程。

当前已完成：

- `/support` 赞助页、`/support/result` 支付结果页、`/supporters` 支持者墙和 `/me/sponsorships` 个人赞助记录已完成。
- 后台赞助方案、赞助订单、支付日志和支持者资料管理已完成。
- P1 阶段模拟支付、后台手动处理订单和支持者身份有效期基础已完成。

仍未开发：

- 真实微信支付、支付宝或其他第三方支付 API。
- 支付回调验签、退款 API、发票、续费提醒、优惠码、自定义金额和异常支付对账。
- VIP 复杂权益、后台会员权益管理、付费内容墙或图片下载权益。

状态：基础完成。P1 已完成模拟赞助闭环；真实支付和 VIP 复杂权益仍未开始。

## 第一版 MVP 历史目标

以下记录 P0 / Phase 1 当时的第一版 MVP 目标，已完成；本节不是当前仍未开发清单。

核心闭环包括：

- 管理员可以登录后台。
- 管理员可以上传图片。
- 管理员可以管理图片基础信息。
- 管理员可以创建相册/专题，并为相册选择默认分类。
- 管理员可以为相册手动选择封面图；手动封面只能选择相册内已发布图片；未手动选择时，系统默认从相册内已发布图片中随机选择一张作为封面展示。
- 相册新建后默认草稿；只有已发布相册在前台公开展示，隐藏状态用于临时下架。
- 相册发布前必须至少包含 1 张已发布图片；否则不允许发布，并提示管理员或编辑先上传并发布图片。
- 管理员可以在相册中批量上传图片。
- 批量上传完成后，管理员可以进入批量整理页面，逐图快速补充标题、说明、标签和发布状态；图片说明和标签都可以为空。
- 图片上传后由系统自动重命名，格式为 `YYYYMMDD-HHmmss-6位随机码.原扩展名`。
- 图片标题默认使用系统重命名后的文件名，发布前可修改，也可不修改；标题不允许为空。
- 数据库保留用户上传时的原始文件名，用于后续追溯线索。
- 图片上传后默认进入草稿/待整理状态，不在前台公开展示。
- 管理员或编辑点击发布后，图片立即发布并对前台可见。
- 已发布相册的前台页面只展示已发布图片，不展示仍处于草稿/待整理状态的图片。
- 已发布相册必须始终至少保留 1 张已发布图片；如果图片状态变更、删除或移出相册会导致相册没有已发布图片，后台必须阻止操作，并提示先将相册改为草稿或隐藏。
- 图片加入相册时，自动继承相册默认分类。
- 相册内图片不允许额外手动补充分类，分类完全跟随相册。
- 单独上传图片时，图片必须自行选择 7 个主分类下的子分类，7 个主分类缺一不可。
- 管理员可以维护分类子项、标签和来源等检索维度；赛事、球队、赛季、年份等通过分类子项维护，人物同框通过人物关系标签维护。
- 前台用户和未登录游客可以浏览全部公开内容，包括已发布图片、已发布相册和公开专题。
- 首页需要提供“最新照片”模块，展示最新发布的图片；单独上传且不属于相册的已发布图片也应进入该模块。
- 前台用户可以进入图片详情页。
- 前台用户可以通过关键词、分类、标签、时间、赛事等基础条件检索图片。

第一版当时暂不做：

- 评论。
- 点赞。
- 转发。
- VIP 会员。
- 充值赞助。
- 微信小程序。
- OCR 识别。
- 感知哈希去重。
- 相似图去重。
- 以图搜图。
- 自动从腾讯云数据万象回写全部 AI 识别结果。

这些能力不是放弃，而是等图库核心闭环稳定后，再按阶段加入。

## 已确定决策

- 本文档作为项目路线图与开发进度的唯一主入口。
- 第一版 MVP 只做图库核心闭环。
- Phase 1 只创建图库核心表；P1 已逐步补充互动、评论、审核、通知、排行榜和赞助支持基础表，AI 分析和系统任务相关表仍按后续切片确认。
- Phase 1 固定 7 个必选主分类：生涯阶段、赛事、赛季、年份、场景、图片类型、来源平台。
- Phase 1 不允许后台随意新增第 8 个主分类；后续如需新增主分类，必须先更新产品文档、数据库约束和旧数据补齐方案。
- 后台允许在 7 个固定主分类下自由新增、编辑和排序子分类。
- 每个主分类都必须预置 `待补充` 子分类，用于资料暂时不完整、需要后续考古补充的图片；信息不知道时也必须选择对应主分类下的 `待补充`，不能留空。
- 若后续用户在评论或其他反馈中补充了可靠信息，管理员或编辑可以将 `待补充` 修改为已有子分类，或先新增子分类再重新选择。
- Phase 1 图片支持多分类，本质是每个主分类选择一个子分类；标签独立存在，图片也支持多标签。
- Phase 1 图片可以加入一个或多个相册，通过 album_photo 维护关系。
- Phase 1 加入相册/专题功能；相册必须选择 7 个主分类下的子分类，7 个主分类缺一不可；相册内上传形成的图片记录完全同步相册分类，相册内图片不额外补充分类。
- Phase 1 相册封面可以手动选择；手动封面只能选择相册内已发布图片；未手动选择时，系统默认从相册内已发布图片中随机选择一张作为封面展示。
- Phase 1 相册需要发布状态：`draft` 草稿、`published` 已发布、`hidden` 隐藏；新建相册默认草稿，只有已发布相册在前台展示。
- Phase 1 相册发布前必须至少包含 1 张已发布图片；否则不允许发布，并提示管理员或编辑先上传并发布图片。
- Phase 1 已发布相册的前台页面只展示已发布图片，不展示仍处于草稿/待整理状态的图片。
- Phase 1 已发布相册必须始终至少保留 1 张已发布图片；如果图片状态变更、删除或移出相册会导致相册没有已发布图片，后台必须阻止操作，并提示先将相册改为草稿或隐藏。
- 单独上传图片时，图片必须自行选择 7 个主分类下的子分类，7 个主分类缺一不可，并可设置多个标签。
- Phase 1 允许后台自由新增、编辑和排序标签，但每个标签必须归属一个标签类型。
- Phase 1 预置 8 个标签类型：动作、情绪、画质、人物关系、荣誉、画面内容、服装/装备、地点。
- Phase 1 图片标签可以为空；标签用于补充细节，不阻塞整理和发布。
- Phase 1 上传图片时不做重复检测、不做哈希拦截、不做感知哈希检测、不做相似图检测；上传一次就是一条新的图片记录。
- 同一视觉图片可以重复上传到不同相册，各自作为独立图片记录管理，各自跟随所在相册分类并维护自己的标题、说明和标签；相似图去重后续在后台管理。
- 相似图去重作为后续后台管理能力，不进入 Phase 1 上传流程。
- Phase 1 必须支持批量上传到相册；上传完成后进入批量整理页面，支持逐图编辑标题、说明、标签和发布状态。
- 批量整理页面不提供相册内图片分类编辑，分类由相册统一决定。
- Phase 1 图片上传后默认进入草稿/待整理状态；点击发布后立即进入已发布状态并对前台可见。
- Phase 1 单独上传且不属于任何相册的图片，只要状态为已发布且 7 个主分类已选满，也应在前台图片列表、分类检索和首页“最新照片”模块中展示。
- Phase 1 图片上传后系统自动重命名文件，格式为 `YYYYMMDD-HHmmss-6位随机码.原扩展名`；标题默认使用重命名后的文件名，发布前可改可不改；标题不允许为空；数据库保留原始文件名。
- Phase 1 图片说明可以为空；说明用于补充背景、考古线索或来源备注，不阻塞整理和发布。
- 评论、点赞、收藏、转发、互动排行榜、勋章/成就、VIP、充值赞助、微信小程序、OCR、相似图推荐、相似图去重和以图搜图都不进入第一版；其中评论、点赞、收藏、分享基础能力、互动排行榜、支持者赞助闭环和勋章 / 成就基础已在 P1 起步切片中推进。
- 前台图片详情页永远不做默认下载按钮；P0 不做，后续阶段也不作为默认公开能力。
- Phase 1 允许未登录用户浏览全部公开内容，包括已发布图片、已发布相册和公开专题。
- 技术栈采用 Laravel + Inertia.js + Vue 3 + TypeScript + Tailwind CSS。
- 后台第一版使用 Filament，不自建后台管理系统。
- 本地开发阶段先用 SQLite，降低新手环境搭建成本。
- 后台默认语言使用简体中文。
- 后续涉及腾讯云 COS、数据万象、微信支付、短信等第三方服务时，先做接口边界和配置文档，再接真实服务。

## 风险与注意事项

- 项目容易功能膨胀，所有新增功能必须先判断是否影响 MVP 核心闭环。
- 图片版权和来源要尽早设计字段，避免后期补数据成本过高；P0 来源管理字段保持克制，只记录原始链接、原始发布日期、版权备注和内部备注。
- 图片分类体系会决定后续检索体验，不能只按“照片类型”粗略分类。
- 微信小程序审核存在不确定性，不能作为第一版上线依赖。
- 以图搜图、相似图去重和 OCR 都属于增强能力，不能阻塞第一版图库管理上线。
- 支付和会员涉及资金链路，必须在功能设计、合规说明、异常处理明确后再开发。
- 后续 AI agent 开发必须先阅读本文档、`CONTEXT.md` 和相关 PRD/架构文档，再开始修改代码。
