# 开发规范与协作规范

## 1. 代码规范

- PHP 遵循 Laravel 默认风格。
- 类名、方法名、变量名使用英文。
- 业务注释和文档使用中文。
- 不写无意义注释，只在复杂业务、权限、支付、队列、外部服务处写解释。
- 不把第三方密钥写入代码。
- 所有配置走 `.env`。

## 2. Laravel 规范

- 业务逻辑不要堆在 Controller。
- 复杂业务放到 `app/Actions` 或 `app/Services`。
- 队列任务放到 `app/Jobs`。
- 权限判断使用 Policy 或明确的权限方法。
- 后台 CRUD 优先用 Filament Resource。
- 前台页面优先放在 `resources/js/pages`，使用 Inertia 页面组件。
- 前台共享组件放在 `resources/js/components`，不要把页面私有组件过早抽象成全局组件。
- 前台样式使用 Tailwind CSS 和语义化组件封装，避免散落大量一次性 class 造成难维护。
- 数据库变更必须通过 migration。
- 枚举状态要集中定义，避免字符串散落。

## 3. 测试规范

采用行为测试优先：

- 登录、权限、上传、搜索、评论、支付回调必须有 Feature Test。
- 测试用户可见行为，不测试私有方法。
- 不为了覆盖率写脆弱测试。
- 一个测试验证一个主要行为。

参考 Laravel Testing：https://laravel.net.cn/docs/12.x/testing

## 4. 安全规范

- 后台必须限制管理员/编辑员访问。
- 上传文件必须校验 MIME、扩展名、大小。
- 评论必须限流和审核。
- 支付回调必须验签和幂等。
- COS 上传路径不能由用户完全控制。
- 原图访问策略必须可控。
- 删除图片优先软删除或归档，不直接物理删除。

## 5. 新手协作规范

AI 每次完成任务后必须说明：

- 改了哪些文件。
- 实现了什么能力。
- 怎么本地验证。
- 有哪些风险。
- 下一步建议。

用户不需要理解所有代码细节，但必须能理解“这个任务是否完成、如何检查、下一步做什么”。

## 6. 开发顺序建议

1. 初始化 Laravel 项目。
2. 选择 Laravel Vue Starter Kit，启用 Inertia + Vue + TypeScript + Tailwind。
3. 接入 Filament 后台。
4. 设计并迁移图库核心表。
5. 实现管理员/编辑员权限。
6. 实现图片上传到可配置存储，本地存储和腾讯云 COS 两种方式都可切换；生产环境优先 COS/CDN。
7. 实现前台图库浏览。
8. 实现搜索筛选。
9. 加入用户登录。
10. 加入收藏、点赞、评论、分享、通知、互动排行榜和勋章/成就。
11. 加入赞助支持。
12. 加入数据万象队列处理。
13. 加入小程序 API。


## 7. 任务拆分与项目管理

项目任务必须使用垂直切片：一个任务要能独立演示，并尽量覆盖必要的数据、后端、页面/接口和测试。不要创建长期不可演示的横向任务，例如只建一堆空表、空模型或空页面。

本地任务文件放在 `.scratch/messi-gallery/`。任务状态使用：`needs-triage`、`needs-info`、`ready-for-agent`、`ready-for-human`、`wontfix`。

任务文件建议包含：背景、用户价值、范围、不做什么、验收标准、测试要求、依赖和状态。

Git 分支可以简化为 `main + feature/*`。复杂协作后再引入 `develop`、`fix/*`、`docs/*`。

`CHANGELOG.md` 按日期记录 `Added`、`Changed`、`Fixed`、`Verified`。完成文档合并、数据库迁移、功能切片和重要规则变更时都要更新。

## 8. AI 协作流程

1. 读取 `AGENTS.md`、`CONTEXT.md` 和当前任务相关主文档。
2. 总结任务目标和不做什么。
3. 检查现有代码和文档，不凭空猜测。
4. 实现一个可验证的小切片。
5. 运行测试或说明无法测试的原因。
6. 汇报改动、验证方式、风险和下一步。

## 8.1 切片确认与进度同步硬规则

`docs/project/development-progress.md` 是唯一进度事实源。开始任何开发前，必须先读取其中的“当前唯一开发入口”，并核对 `docs/ui/page-map.md` 与 `.scratch/messi-gallery/` 任务文件是否一致。

功能切片必须按固定节奏推进：确认稿 -> 用户确认 -> 开发 -> 测试/构建 -> 文档收口 -> 下一切片确认稿。确认稿必须一次性覆盖字段、按钮、筛选、排序、状态、权限、验收标准、交互方式和 UI/UX 风格，不允许一轮只问一个细碎问题，也不允许当前切片未收口就进入下一切片。

编号只能作为文档定位辅助，不能作为任务状态依据。沟通和记录当前任务时必须同时写清功能名和路由，例如“前台图库列表 `/photos`”；如果历史对话编号与现有文档编号冲突，以功能名、路由和主进度文档为准。

每个切片收口时必须同步四处状态：

- `docs/project/development-progress.md` 的当前状态、当前唯一开发入口、下一步计划和待确认问题。
- `docs/ui/page-map.md` 的对应确认稿状态和 P0 总体验收规则。
- `.scratch/messi-gallery/` 中相关任务文件的验收标准和状态。
- `CHANGELOG.md` 的 Added、Changed、Verified 记录。

如果发现这些位置不一致，必须先修正文档进度口径，再继续开发代码。
## 9. 新手注意事项

- 不要一次性让 AI 做完整大项目。
- 每次只做一个垂直切片。
- 不理解命令时先问“这条命令会改什么”。
- 涉及支付、删除、数据库迁移、权限变更和批量处理图片时必须先确认影响范围。


## 10. 文档维护硬规则

- 禁止新增新的说明类文档文件，包括但不限于 `docs/` 下的新增 Markdown、额外规格文档、临时分析文档、页面细化文档、ADR 拆分文档。
- 任何产品、页面、数据库、架构、开发规范、部署、第三方服务、进度和任务拆分内容，都必须合并进现有主文档。
- 需要记录新决策时，优先修改对应主文档：产品写 PRD，页面写 `docs/ui/page-map.md`，数据库写 `docs/database/schema.md`，进度写 `docs/project/development-progress.md`，开发规则写本文档，架构写 `docs/architecture/technical-architecture.md`。
- 如确实认为必须新增文档文件，必须先向用户说明为什么现有主文档无法承载，并取得明确同意；默认答案是不新增。
